# 0103. The Cluster Autoscaler salvo keeps the 1m budget when a later option does not start

- **Status:** Accepted
- **Date:** 2026-09-23
- **Code:** `deploy/k8s/cluster-autoscaler.yaml`; `deploy/k8s/check-cluster-autoscaler-salvo-early-stop.sh`

## Context

[0102](0102-cluster-autoscaler-scale-up-salvo.md) left this gap: each salvo iteration is still one expander option. If that call uses the whole `1m` budget, the snapshot update fails, or the scale-up is not successful, the pods still waiting use the next main loop. Inventory on cluster-autoscaler v1.36.1 (`core/static_autoscaler.go` `runScaleUpSalvo`, `processors/status/scale_up_status_processor.go` `WasSuccessful`, `config/flags/flags.go`, `loop/trigger.go`, `core/scaleup/orchestrator/orchestrator.go` `IsNodeGroupReadyToScaleUp`; FAQ "How does scale-up work?"; the 1.36.0 release note for `#9606`; the image tag in this repo):

| Knob | What v1.36.1 does | What this slice does with it |
|------|-------------------|------------------------------|
| `--salvo-scale-up-budget` | Duration, default `1m`. The flag text is "Maximum time CA spends on subsequent scale ups in a single CA loop." `runScaleUpSalvo` starts `context.WithTimeout` before iteration 0. The context is not passed into `runSingleScaleUp`, so the call is not cancelled. After a successful iteration that still has pods left, `salvoCtx.Err()` is read. A deadline stops the salvo before `addLatestScaleUpResultsToClusterSnapshot` and before the next option. The first call's wall time counts. `#9606` and the 1.36.0 release note say the budget keeps the salvo from starving the rest of the loop. There is no documented value other than the `1m` default | Stay `--salvo-scale-up-budget=1m`. `0s`, `5m`, and `15m` are refused. Any other duration is refused |
| `--max-node-provision-time` | Duration, default `15m`. The FAQ says a requested node is expected to appear within this time. After that, CA drops an unregistered node from simulation and may scale a different group on a later loop. The salvo injects upcoming nodes into the snapshot immediately. It does not wait for the instance to register. This clock is not the salvo budget | Unset, so the `15m` default stays. Any value is refused. Copying `15m` into the salvo budget is refused |
| `--max-node-startup-time` | Duration, default `15m`. Time from registration until the node is ready. Not the salvo clock | Unset. Any value is refused |
| `--max-binpacking-time` | Duration, default `5m`. Caps binpacking inside one scale-up. A call that runs longer than `1m` makes the budget check fail before the next option. Upstream does not say to raise the salvo budget to this cap | Unset. Any value is refused |
| `--max-nodegroup-binpacking-duration` | Duration, default `10s` per node group. This pool is one similar group per zone. Under that cap, binpacking two zones plus the cloud resize fits in the `1m` budget, so a second option still starts under that timing. Raising the cap is how one call uses the whole budget | Unset. Any value is refused |
| `--frequent-loops-enabled` | Bool, default true. `LoopTrigger.Wait` returns immediately when `LastScaleUpTime` is not before the previous run. `instrumentedScaleUp` sets that time only when the result is `ScaleUpSuccessful`. An unschedulable pod whose condition transition is still inside 10s can also wake the loop. False waits on `--scan-interval` | Stay `--frequent-loops-enabled=true`. `false`, a bare flag, and a missing flag are refused |
| `--initial-node-group-backoff-duration` | Duration, default `5m`. First backoff after a new node failed to start. `IsNodeGroupReadyToScaleUp` then skips that group (`BackoffReason`). The skip is inside a later `ScaleUp`. It does not resume a salvo that already stopped | Unset. Any value is refused |
| `--max-node-group-backoff-duration` | Duration, default `30m`. Cap on that backoff | Unset. Any value is refused |
| `--node-group-backoff-reset-timeout` | Duration, default `3h`. Time after the last failed scale-up when the backoff duration resets | Unset. Any value is refused |
| `--provisioning-request-initial-backoff-time`, `--provisioning-request-max-backoff-time`, `--provisioning-request-max-backoff-cache-size` | Defaults `1m`, `10m`, and `1000`. They retry ProvisioningRequest objects. `--enable-provisioning-requests` defaults false | Unset. This cluster does not enable provisioning requests. Any of these flags is refused |
| `--parallel-scale-up` | Bool, default false. The flag text says experimental and that it may not work on some cloud providers. It runs groups from one scale-up plan concurrently. The plan is still one `BestOption`. It does not start the option for pods that option did not place | Unset. Any value is refused |
| `--new-pod-scale-up-delay` | Duration, default `0s`. A positive delay leaves younger pods out of scale-up. `allPodsAreNew` then sets `ScaleUpInCooldown`. `WasSuccessful` is false unless the result is `ScaleUpSuccessful`, so the salvo stops before an option | Unset. Any value is refused |
| `--scan-interval` | Default `10s`. Spaces a main loop. It does not add an option inside the salvo | Unset, as in [0102](0102-cluster-autoscaler-scale-up-salvo.md) |

`WasSuccessful` is `Result == ScaleUpSuccessful`. `runScaleUpSalvo` ends, and does not start another option, when the scale-up returns an error, when the result is not successful, when the triggering-pod list is empty, when the budget context is already done, or when the snapshot update returns an error. No flag continues past those stops. A longer budget is not justified: the only documented duration is the `1m` default, and that default exists so the salvo does not starve the rest of the loop. The `15m` provision wait and the `5m` binpacking cap measure other work.

After a successful iteration, the next main loop starts immediately because `--frequent-loops-enabled=true` and `LastScaleUpTime` was set. Pods the stopped salvo did not place are that next loop. After a result that is not successful, `LastScaleUpTime` is not updated. The next wake is a fresh unschedulable pod, or else the `10s` scan interval. `--frequent-loops-enabled=false` would put even the successful case on that interval.

A zone already at max 10 is skipped inside `ScaleUp` (`MaxLimitReached`). That ceiling is not this slice. On two hostnames the HPA floor is still 2 and 1. That floor is not this slice. Do not set `minDomains`. Required hostname anti-affinity is not the follow-up. Required zone anti-affinity is not the follow-up.

The [0101](0101-cluster-autoscaler-leader-scale.md) flags stay `--balance-similar-node-groups=true`, `--expander=least-waste`, and `--skip-nodes-with-system-pods=false`. The [0102](0102-cluster-autoscaler-scale-up-salvo.md) flags stay `--salvo-scale-up=true`, `--salvo-scale-up-budget=1m`, and `--frequent-loops-enabled=true`. There is no priority expander ConfigMap. ## Decision

**The 1m salvo budget stays. Node-provision time and node-group failure backoff stay at the v1.36.1 defaults, unset on the command. No flag continues a salvo after the budget is already gone, the snapshot update fails, or the scale-up is not successful. Pods still waiting use the next main loop. `--frequent-loops-enabled=true` stays, so a loop that did scale up starts that next pass immediately. Kind and minikube do not apply this file.**

1. **Budget stays `1m`.** `--salvo-scale-up-budget=1m` stays, one argument, written out. That is the v1.36.1 default and the only duration the 1.36.0 note documents. `0s` expires before a second option. `5m` copies `--max-binpacking-time`. `15m` copies `--max-node-provision-time`. Each of those is refused, and so is any other duration. `--salvo-scale-up=true` stays. A bare flag and `false` are refused.
2. **Provision and binpacking clocks stay the defaults.** `--max-node-provision-time`, `--max-node-startup-time`, `--max-binpacking-time`, and `--max-nodegroup-binpacking-duration` stay unset. The defaults are `15m`, `15m`, `5m`, and `10s`. Setting any of them is refused. The `10s` per-group cap is what keeps two zones of binpacking inside the `1m` budget under normal timing. The salvo still injects upcoming nodes without waiting for them to register.
3. **Failure backoff stays the defaults.** `--initial-node-group-backoff-duration`, `--max-node-group-backoff-duration`, and `--node-group-backoff-reset-timeout` stay unset. The defaults are `5m`, `30m`, and `3h`. They apply after a new node failed to start. They do not resume a stopped salvo. Shortening them is refused. The provisioning-request backoff flags and `--enable-provisioning-requests` stay unset.
4. **Flags that do not add the second option stay unset.** `--parallel-scale-up` stays unset. `--new-pod-scale-up-delay` stays unset. `--scan-interval` stays unset. `--frequent-loops-enabled=true` stays. `--balance-similar-node-groups=true`, `--expander=least-waste`, and `--skip-nodes-with-system-pods=false` stay. There is no priority expander ConfigMap.
5. **When the salvo still stops.** An error, a result other than `ScaleUpSuccessful`, an empty triggering-pod list, a budget context that is already done, or a snapshot update error ends the salvo. The next main loop is the retry. After a successful scale-up that then stops, frequent loops start that loop immediately. A zone at max 10 still cannot grow. `minDomains` stays unset. Do not set minDomains.
6. **What this slice does not change.** Replicas stay 2. Leader election stays on. The image stays `registry.k8s.io/autoscaling/cluster-autoscaler:v1.36.1`. The zone item stays. Required hostname anti-affinity stays. Required zone anti-affinity is not set. The file stays out of the kustomization. No live AWS apply.
7. **Kind and minikube.** This file stays out of the kustomization. `kubectl apply -k deploy/k8s` does not install it. Kind and minikube do not apply this file. Do not add it to make a laptop scale. Do not set `minDomains`. Do not taint a kind or minikube node.
8. **Verify without a cluster.** `check-cluster-autoscaler-salvo-early-stop.sh` fails when salvo is missing, bare, or `false`, when the budget is missing or not `1m` (including `0s`, `5m`, and `15m`), when frequent loops are missing or not `true`, when a node-group backoff flag, a provision-time flag, a binpacking-time flag, `--parallel-scale-up`, `--new-pod-scale-up-delay`, or a provisioning-request backoff flag is set, when this ADR drops the early-stop record, when `minDomains` is set, or when `kustomization.yaml` lists the file. `check-cluster-autoscaler-salvo-early-stop.test.sh` proves those regressions. No `kubectl apply` and no `terraform apply`.

## Consequences

- Under the unset `10s` per-node-group binpacking cap, a second least-waste option still starts in the same main loop when the first call finishes inside `1m` and the scale-up succeeds and the snapshot update succeeds. That is the normal path for one similar group per zone.
- If the first call uses the whole `1m`, the snapshot update fails, or the scale-up is not successful, the salvo stops. v1.36.1 has no flag that continues it. Pods still waiting use the next main loop.
- A successful scale-up sets `LastScaleUpTime`, so `--frequent-loops-enabled=true` starts that next loop without waiting out `--scan-interval`. A result that is not successful does not set that time. The wake is then a fresh unschedulable pod, or the `10s` scan interval.
- Node-group backoff stays `5m`, then up to `30m`, resetting `3h` after the last failure. A backed-off group is skipped on a later `ScaleUp`. It is not given a second option inside the salvo that already stopped.
- The per-zone max is [0104](0104-per-zone-node-max.md). On two hostnames the HPA floor is still 2 and 1. That floor is a later gap.
- Kind and minikube do not apply this file. One labeled zone still schedules both pods when two hostnames exist. Do not set `minDomains`. Required zone anti-affinity is not set.
- Setting the budget to `0s`, `5m`, or `15m`, turning salvo or frequent loops off, or pinning a backoff, provision, or binpacking duration fails `check-cluster-autoscaler-salvo-early-stop.sh`.
- Catalog stays 221. No Rui sprites. `_*.py` stay untracked.
- **Next gap:** moved. The per-zone max is [0104](0104-per-zone-node-max.md). The Pending standby never holds the lease ([0110](0110-cluster-autoscaler-pending-lease.md)). One labeled zone still schedules both Cluster Autoscaler pods when two hostnames exist. Do not set `minDomains`. Required hostname anti-affinity is not the follow-up. Required zone anti-affinity is not the follow-up. On two hostnames the HPA floor is 2 and 1, so two pods of one color can still share a node. The kube-proxy managed addon schema still rejects `tolerations`, so coverage between applies depends on the [0097](0097-kube-proxy-toleration-hook.md) hook and on the flag being true. One labeled zone still schedules both metrics-server pods when two hostnames exist. One hostname still schedules every API pod of the live color. The serving certificate chains to APIService `caBundle` and its DNS SAN is `metrics-server.kube-system.svc` ([0111](0111-metrics-server-serving-cert-chain.md)). A kubelet certificate that does not chain to `metrics-server-kubelet-ca` still leaves `kubectl top` empty.
