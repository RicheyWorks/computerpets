# 0104. Each API zone can grow past the old max of 10

- **Status:** Accepted (the per-zone min of 1 is [0105](0105-api-hostname-floor.md); the max of 20 stays)
- **Date:** 2026-09-23
- **Code:** `deploy/terraform/modules/node_pool/main.tf`; `deploy/k8s/check-cluster-autoscaler-zone-max.sh`

## Context

Inventory on `main` tip `65741cd11` (cluster-autoscaler v1.36.1, `cloudprovider/aws/auto_scaling_groups.go` `buildAsgFromAWS`, `cloudprovider/aws/aws_manager.go` `buildNodeFromTemplate` and `parseASGAutoDiscoverySpec`; the node-pool module and the IRSA deny list in this repo):

A keeper cannot raise it without editing the local |

EKS writes the node group's `scalingConfig.maxSize` onto that managed group. `eks:DescribeNodegroup` copies labels, taints, and tags onto the scale-up template. Why 10 starved. The integer is the HPA pod ceiling, not unused node slots. One zone can be asked to hold all of these when the other zone cannot take the pod (one domain, or the crowded zone failing `DoNotSchedule` / `maxSkew` 1):

| Pods forced into the zone | Count | Why they can consume the old max |
|---------------------------|-------|----------------------------------|
| Live-color API pods | 10 | `maxReplicas`. [0083](0083-cluster-autoscaler.md) sized one node per replica |
| Cluster Autoscaler | 2 | Required hostname anti-affinity. Hard zone spread. Both land here when the other zone is gone or crowded |
| metrics-server | 2 | The same hostname rule and the same zone item |

That is 14 nodes at one pod per node, and the old max is 10. After the API allowance is used, the zone is `MaxLimitReached` and the system pods stay Pending. Default workers are `t3.medium` (2 vCPU, 4 GiB). API requests are `250m` / `512Mi` (memory limit `1Gi`). Cluster Autoscaler requests `100m` / `300Mi`. metrics-server requests `100m` / `200Mi`. `aws-node` and `kube-proxy` sit on every node. Pods can share a node, and they can also refuse the next pod while the zone is already at 10. Either way the group does not grow.

20 is twice the HPA ceiling. The first 10 stays the one-zone API allowance. The second 10 is headroom so a zone already at the old max can still grow: the four system pods that cannot share a hostname, and nodes that DaemonSets and the API request leave unable to take another pod. Fourteen would cover the named pods once and then stick on the next Pending pod. Twenty is one full extra HPA-sized burst. It is not the account Auto Scaling maximum.

Cost stays a cap, not a target. `min_size` stays 1. Create-time `desired_size` stays 1. The leader adds a node only for a Pending pod. Two zones at the cap are 40 on-demand nodes of the configured general-purpose type (default `t3.medium`). Twenty-one and above are refused. The value is a local, not a root variable: a `tfvars` override could plan 10 while this file still said 20, and the checks read the file. A variable that only accepts 20 is a constant. The local is that constant.

## Decision

**Each API zone's managed node group `max_size` is 20. That is the growth ceiling Cluster Autoscaler reads as the Auto Scaling group's `MaxSize`. It is twice `hpa.yaml` `maxReplicas` (10) and at least that pod count. `min_size` stays 1. The leader cannot raise the ceiling. Kind and minikube do not apply the autoscaler file. No live AWS apply.**

The `min_size` stays 1 clause in that decision is the part [0105](0105-api-hostname-floor.md) replaces. The max of 20 in this ADR is unchanged.

1. **Ceiling.** `max_size_per_zone` is the local `20`. The node group sets `scaling_config.max_size` to that local, not to a second literal. `zone-max-nodes=20` names it. `hpa-max-replicas=10` stays the pod ceiling the number is measured against. A value of 10 is the starved ceiling and is refused. A value below `maxReplicas` is refused. A value other than 20, including 0, 4, 9, 21, and 100, is refused. There is no `variable "max_size_per_zone"`.
2. **How the leader discovers it.** The two discovery tags still select the managed Auto Scaling group. `autoscaling:DescribeAutoScalingGroups` stays on the describe list. v1.36.1 `buildAsgFromAWS` copies `MaxSize` from that response. `eks:DescribeNodegroup` stays on the describe list for the pool label and the taint. It is not the max. `eks:UpdateNodegroupConfig` stays denied, with `autoscaling:UpdateAutoScalingGroup`, so the leader cannot write a higher ceiling. `SetDesiredCapacity` stays tag-scoped and stops at the group's `MaxSize`.
3. **What stays.** `min_size_per_zone` stays 1, and it stays below the max. Create-time `desired_size` stays 1 and ignored after create. At least two zones. One group per subnet. The same `instance_types` list. The label `computerpets/node-pool=api`. The `NoSchedule` taint. `--balance-similar-node-groups=true`, `--expander=least-waste`, `--skip-nodes-with-system-pods=false`, `--salvo-scale-up=true`, `--salvo-scale-up-budget=1m`, and `--frequent-loops-enabled=true` stay. `--max-nodes-total`, `--cores-total`, and `--memory-total` stay unset.
4. **What this slice does not change.** HPA stays min 3 / max 10. On two hostnames the floor is still 2 and 1. The API PDB stays `minAvailable: 2`. Replicas stay 2. The zone item stays. `minDomains` stays unset. Do not set minDomains. Required hostname anti-affinity stays. Required zone anti-affinity is not set. The file stays out of the kustomization. No live AWS apply. A cluster whose group is still at 10 stays there until a keeper applies this max.
5. **Kind and minikube.** The autoscaler file stays out of the kustomization. `enable_node_pool=false` does not plan the groups or the role. Kind and minikube do not apply this file. Do not add it to make a laptop scale. Do not set `minDomains`. Do not taint a kind or minikube node.
6. **Verify without a cluster.** `check-cluster-autoscaler-zone-max.sh` fails when `max_size_per_zone` is not 20 (including the old 10), when that local is not the only one, when `scaling_config.max_size` is not the local, when the max is below `maxReplicas`, when `min_size` is not 1, when `DescribeAutoScalingGroups` drops off the describe list, when `UpdateNodegroupConfig` is no longer denied, when a root or module variable can override the local, when `--max-nodes-total`, `--cores-total`, or `--memory-total` is set, when the balance, least-waste, or salvo pins drop, when `minDomains` is set, or when `kustomization.yaml` lists the file. `check-cluster-autoscaler-zone-max.test.sh` proves those regressions. No `kubectl apply` and no `terraform apply`.

## Consequences

- A zone that has already reached 10 nodes can still grow, up to 20, when hard zone spread leaves a Pending API pod or a Pending Cluster Autoscaler pod with no other group.
- The leader still skips a zone whose desired capacity is already `MaxSize`. Twenty is the new stop. It is not unlimited.
- `DescribeAutoScalingGroups` is the read. Changing the Terraform local does nothing to a live group until a keeper applies it. This slice does not apply.
- `min_size` stays 1, so a zone is not scaled to zero. Two zones still mean at least two workers. The billable count stays at the nodes the leader has added for Pending pods, not at 20.
- `--max-nodes-total`, `--cores-total`, and `--memory-total` stay unset so a cluster-wide cap cannot restore the stop under 20 per zone.
- Kind and minikube do not apply the autoscaler file. One labeled zone still schedules both Cluster Autoscaler pods when two hostnames exist. Do not set `minDomains`. Required zone anti-affinity is not set.
- The healthy-zone hostname floor is [0105](0105-api-hostname-floor.md). The one Ready zone is [0106](0106-api-single-zone-hostname-floor.md).
- Setting the local back to 10, dropping it under the HPA ceiling, raising it past 20, hardcoding `scaling_config.max_size`, or pinning a cluster-wide node cap fails `check-cluster-autoscaler-zone-max.sh`.
- Catalog stays 221. No Rui sprites. `_*.py` stay untracked.
