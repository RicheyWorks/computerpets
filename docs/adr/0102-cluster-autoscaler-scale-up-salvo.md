# 0102. The Cluster Autoscaler leader scales another group in the same loop

- **Status:** Accepted
- **Date:** 2026-09-23
- **Code:** `deploy/k8s/cluster-autoscaler.yaml`; `deploy/k8s/check-cluster-autoscaler-scale-up-salvo.sh`

## Context

[0101](0101-cluster-autoscaler-leader-scale.md) left this gap: the leader still chooses one node group per scale loop. Other Pending pods can win `least-waste` for that loop, so a Pending Cluster Autoscaler standby waits until a later loop. Inventory on cluster-autoscaler v1.36.1 (`static_autoscaler.go`, `config/flags/flags.go`, `core/scaleup/orchestrator/orchestrator.go`, `loop/trigger.go`; the image tag in this repo):

| Knob | What v1.36.1 does | What this slice does with it |
|------|-------------------|------------------------------|
| One `ScaleUp` call | `prepareScaleUp` keeps the options that can take at least one pod, then `ExpanderStrategy.BestOption` returns one option. `balanceScaleUps` may split that option across similar groups that can schedule the same pods. It does not start a second option for pods that only fit the underfilled zone | Unchanged. `--balance-similar-node-groups=true` and `--expander=least-waste` stay ([0101](0101-cluster-autoscaler-leader-scale.md)) |
| `--salvo-scale-up` | Bool, default false. Added in 1.36.0 (`#9606`) and present on v1.36.1. When true, `runScaleUpSalvo` calls `runSingleScaleUp` again for the pods the previous option did not place. Triggering pods are removed. Upcoming nodes are injected and those pods are scheduled onto them, so the next call bin-packs against that snapshot (`tryToScheduleOnExistingNodes`). The 1.36.0 note calls the flag experimental. The default in v1.36.1 is still false | Set `--salvo-scale-up=true` |
| `--salvo-scale-up-budget` | Duration, default `1m`. The timeout is checked after a successful iteration, before the next one. A budget that is already expired skips the second group | Set `--salvo-scale-up-budget=1m`. `0s` and `1s` are refused |
| Priority expander and ConfigMap `cluster-autoscaler-priority-expander` | Static priorities by node-group name or regex. The underfilled zone moves. Equal priorities fall through. A chain such as `priority,least-waste` changes the [0101](0101-cluster-autoscaler-leader-scale.md) expander pin. Ties after a chain break at random | Not created. The Role may still name the ConfigMap. The manifest has no ConfigMap. The expander arg stays `least-waste` |
| `--max-nodes-per-scaleup` | Int, default 1000. Caps how many nodes one option may add. It does not start a second group. There is no `--max-scale-up` and no `--max-scale-up-parallelism` | Unset |
| `--max-scale-down-parallelism` | Scale-down only. Default 10 | Unset |
| `--scan-interval` | Default 10s (`DefaultScanInterval`). It spaces a main loop when nothing else wakes it. It does not add a second group inside the loop | Unset, so the default stays. A value other than `10s` is refused |
| `--frequent-loops-enabled` | Bool, default true. After a scale-up, `LoopTrigger.Wait` returns immediately because `LastScaleUpTime` is not before the previous run. An unschedulable pod can also wake the loop. `--frequent-loops-enabled=false` puts that wake back on `--scan-interval` | Set `--frequent-loops-enabled=true` so deleting the arg cannot hide the pin |
| `--aws-use-static-instance-list` | AWS instance-type catalog. Default false. It does not change how many groups a loop resizes | Unset |

v1.36.1 still starts the loop only on the replica that holds the lease. A Pending pod does not hold it. The standby is not the scaler. Each salvo iteration still uses `least-waste` and similar-group balance. Hard zone spread still drops the crowded zone's template for this pod. The second iteration asks for the underfilled zone when that zone is the option that can take the pods still waiting, and when the new node from the first iteration cannot take them.

This slice does not reopen presence/CSP, Hikari/replica pool sizing, bundle zip, cosign, CDN edge, secrets rotation, VerifyFieldBounds, ClientAddress, rate-limit bucket sizes, the machine/admin HMAC, the nonce store, the download JWT `jti`, the WAF ACL, Redis AUTH, Postgres JDBC SSL, API listener TLS, the HPA metrics and replica range, the API PDB `minAvailable`, the API hostname/zone topology spread, the metrics-server zone `DoNotSchedule` item, the node-pool pin or taint, Cluster Autoscaler replica count, required hostname anti-affinity, leader election, node-pool pin, and disruption budget, aws-node, vpc-cni, or the kube-proxy reassert hook beyond this cross-link. The [0101](0101-cluster-autoscaler-leader-scale.md) flags stay `--balance-similar-node-groups=true`, `--expander=least-waste`, and `--skip-nodes-with-system-pods=false`. Required zone anti-affinity stays unset. Required hostname anti-affinity is not the follow-up. Do not set `minDomains`. Catalog stays 221. No storefront. No DirectX 12 / Vulkan / Solana. No Rui sprites.

## Decision

**The scheduled leader keeps least-waste and similar-group balance, and `--salvo-scale-up=true` with `--salvo-scale-up-budget=1m` runs another scale-up in that same loop for pods the first option did not place. `--frequent-loops-enabled=true` stays. There is no priority expander ConfigMap. Kind and minikube do not apply this file.**

1. **Same loop, another option.** `--salvo-scale-up=true` is set. The v1.36.1 default is false. A bare `--salvo-scale-up` is true and is still refused, so the value stays written down. `--salvo-scale-up=false` is refused. Each iteration is one `BestOption` under `--expander=least-waste`. `--balance-similar-node-groups=true` still splits that option only across groups that can schedule the same pods. `--skip-nodes-with-system-pods=false` stays. The image stays `registry.k8s.io/autoscaling/cluster-autoscaler:v1.36.1`, the minor that contains the flag.
2. **Budget.** `--salvo-scale-up-budget=1m` is set. That is the v1.36.1 default. The timer is checked after a successful iteration. `0s` expires before the second group. Any budget other than `1m` is refused.
3. **What does not prefer the underfilled zone by name.** A priority expander ConfigMap is not added. A static list cannot name the zone that is underfilled. `--expander` stays `least-waste`. `priority`, `random`, `most-pods`, `price`, `grpc`, and a comma chain are refused. The Role's `cluster-autoscaler-priority-expander` resource name stays and does not create the ConfigMap.
4. **The wake after this loop.** `--frequent-loops-enabled=true` is set. The v1.36.1 default is true. `--frequent-loops-enabled=false` is refused. `--scan-interval` is unset. A value other than `10s` is refused. `--max-nodes-per-scaleup`, `--max-scale-down-parallelism`, and `--aws-use-static-instance-list` stay unset.
5. **What this slice does not change.** Replicas stay 2. Leader election stays on. `--namespace=kube-system` stays the lease namespace. There is no `--allowed-scheduler-names` and no `--nodes` list. The zone item stays. `minDomains` stays unset. Do not set minDomains. Required hostname anti-affinity stays. Required zone anti-affinity is not set. The pool selector and the taint toleration stay. `minAvailable` stays 1. Node groups stay one similar group per zone. The file stays out of the kustomization. No live AWS apply.
6. **Kind and minikube.** This file stays out of the kustomization. `kubectl apply -k deploy/k8s` does not install it. Kind and minikube do not apply this file. Do not add it to make a laptop scale. Do not set `minDomains`. Do not taint a kind or minikube node.
7. **Verify without a cluster.** `check-cluster-autoscaler-scale-up-salvo.sh` fails when salvo is missing, bare, or `false`, when the budget is missing or not `1m`, when frequent loops are missing or not `true`, when the expander is not `least-waste`, when balance or `skip-nodes-with-system-pods=false` drops, when a priority expander ConfigMap is added, when `--scan-interval` is set to a value other than `10s`, when the image is not v1.36.1, when `minDomains` is set, or when `kustomization.yaml` lists the file. `check-cluster-autoscaler-scale-up-salvo.test.sh` proves those regressions. No `kubectl apply` and no `terraform apply`.

## Consequences

- Other Pending pods can still win the first `least-waste` choice. The pods that choice did not place, including a Cluster Autoscaler standby that only fits the underfilled zone, are a later iteration of the same loop while the budget has time left and the scale-up succeeds.
- Similar-group balance can still grow every zone in the first iteration when the winning pods fit every zone. The next iteration bin-packs against those injected nodes, so a pod that already fits is not a reason to add another node.
- The standby is not the scaler. A Pending replica still does not hold the lease. Only the leader runs the salvo.
- `--salvo-scale-up` is the flag the 1.36.0 release note calls experimental. v1.36.1 still defaults it to false. This manifest turns it on. A snapshot update failure, an unsuccessful scale-up, or an empty triggering-pod list ends the salvo. The pods still waiting then depend on the next main loop.
- `--frequent-loops-enabled=true` starts that next loop immediately after a scale-up. It does not itself scale a second group inside the loop. With the flag false, that wake waits on `--scan-interval` (default 10s).
- A zone already at max 10 cannot grow. A backed-off group is skipped. A node that is still registering is not a second scaler.
- Kind and minikube do not apply this file. One labeled zone still schedules both pods when two hostnames exist. Do not set `minDomains`. Required zone anti-affinity is not set.
- Dropping salvo, shortening or lengthening the budget, turning frequent loops off, switching the expander, or adding the priority ConfigMap fails `check-cluster-autoscaler-scale-up-salvo.sh`.
- Catalog stays 221. No Rui sprites. `_*.py` stay untracked.
- **Next gap:** moved. The early stop when the budget is already gone, the snapshot update fails, or the scale-up is not successful is [0103](0103-cluster-autoscaler-salvo-early-stop.md). A zone already at max 10 cannot grow. The Pending standby never holds the lease ([0110](0110-cluster-autoscaler-pending-lease.md)). One labeled zone still schedules both Cluster Autoscaler pods when two hostnames exist. Do not set `minDomains`. Required hostname anti-affinity is not the follow-up. Required zone anti-affinity is not the follow-up. On two hostnames the HPA floor is 2 and 1, so two pods of one color can still share a node. The kube-proxy managed addon schema still rejects `tolerations`, so coverage between applies depends on the [0097](0097-kube-proxy-toleration-hook.md) hook and on the flag being true. One labeled zone still schedules both metrics-server pods when two hostnames exist. One hostname still schedules every API pod of the live color. The serving certificate chains to APIService `caBundle` and its DNS SAN is `metrics-server.kube-system.svc` ([0111](0111-metrics-server-serving-cert-chain.md)). A kubelet certificate that does not chain to `metrics-server-kubelet-ca` still leaves `kubectl top` empty.
