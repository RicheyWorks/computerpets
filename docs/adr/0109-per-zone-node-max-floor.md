# 0109. The per-zone max of 20 stays above the one-zone floor

- **Status:** Accepted
- **Date:** 2026-09-23
- **Code:** `deploy/terraform/modules/node_pool/main.tf`; `deploy/k8s/check-cluster-autoscaler-zone-max-floor.sh`

## Context

[0108](0108-api-single-zone-hostname-ceiling.md) left this gap: a zone already at max 20 cannot grow. Restoring a ceiling above 3 reopens the refused bills and is not the follow-up. Inventory on `main` tip `7209fd437` (cluster-autoscaler v1.36.1, `cloudprovider/aws/auto_scaling_groups.go` `buildAsgFromAWS`; the node-pool module and the IRSA deny list in this repo):

| Surface | What it did | What it did not do |
|---------|-------------|--------------------|
| `max_size_per_zone` | A local, `20`, copied into `aws_eks_node_group.zone` `scaling_config.max_size`. [0104](0104-per-zone-node-max.md) set that to twice the old `maxReplicas` of 10 | Not a root variable. A keeper cannot raise it without editing the local. Twice the new ceiling of 3 is 6, which is not this local |
| How the leader learns the ceiling | Auto-discovery is the two ASG tags. `buildAsgFromAWS` sets `asg.maxSize` from `DescribeAutoScalingGroups` `MaxSize`. EKS writes `scalingConfig.maxSize` onto that managed group. `eks:DescribeNodegroup` copies labels, taints, and tags. It does not read `scalingConfig.maxSize` | The leader does not read the Terraform local. `eks:UpdateNodegroupConfig` is denied, with `autoscaling:UpdateAutoScalingGroup`, so the leader cannot lift the ceiling. `SetDesiredCapacity` stops at `MaxSize` |
| When growth stops | Desired capacity already at `MaxSize` skips that group inside scale-up (`MaxLimitReached`) | The skip does not run while desired is still the floor of 3 |
| What shares the pool | Live-color API (`maxReplicas` 3), Cluster Autoscaler (replicas 2, required hostname anti-affinity), metrics-server (replicas 2, required hostname anti-affinity). All three select `computerpets/node-pool=api` and tolerate the `NoSchedule` taint. Green stays `replicas: 0`. Postgres and Redis do not select the pool | Not a second color. Not a DaemonSet. `aws-node` and `kube-proxy` sit on every node. They are not extra nodes |
| Kind and minikube | Blue `replicas: 2` on one hostname. `enable_node_pool=false` does not plan the groups. The HPA, the PDB, the autoscaler file, and metrics-server stay out of the kustomization | Must still schedule. This cap is not a laptop node count |

Why the old formula is now under the floor. [0104](0104-per-zone-node-max.md) sized one node per pod that one zone can be asked to hold, then doubled the HPA ceiling for headroom. The HPA ceiling is now 3 ([0108](0108-api-single-zone-hostname-ceiling.md)). Twice 3 is 6. One zone can still be asked to hold these when the other zone cannot take the pod:

| Pods forced into the zone | Count | Why they can consume a node |
|---------------------------|-------|-----------------------------|
| Live-color API pods | 3 | `maxReplicas`. Hostname `maxSkew` 1 on the three floor hostnames is 1 each |
| Cluster Autoscaler | 2 | Required hostname anti-affinity. Hard zone spread. Both land here when the other zone is gone |
| metrics-server | 2 | The same hostname rule and the same zone item |
| Drain node | 1 | In the one-pod-per-node model the node being drained still counts toward `MaxSize` until it is gone. The displaced pod needs one new node |

That is 8. A max of 6 (twice the new ceiling) drops the drain node and one system pod. A max of 7 covers the named pods once and then sticks, which is the shape [0104](0104-per-zone-node-max.md) refused. A max of 3 uses the HPA ceiling as a node cap and drops both system Deployments. All three are under the floor and are refused.

Why 20 stays. The cap is not the bill. `min_size` 3 times two zones is six on-demand workers, paid while idle. Lowering `max_size` from 20 to 8 does not remove any of those six. It does delete the twelve slots past the floor. The design has no pod that asks for slot 9, so those slots are not a target. They are the spare [0104](0104-per-zone-node-max.md) kept so the next Pending pod after the named set is not `MaxLimitReached`. Raising past 20 does not place a pod this design does not have. Twenty-one and above stay refused.

Why `MaxLimitReached` at 20 is unreachable in this design. The leader adds a node only for a Pending pod. On one Ready zone the set above binds on the floor of 3:

| Rule | What the floor already provides |
|------|---------------------------------|
| API hostname `maxSkew` 1 | Three hostnames, three pods, 1 each. Nothing stays Pending |
| Cluster Autoscaler required hostname anti-affinity | Two hostnames. The floor has three |
| metrics-server required hostname anti-affinity | Two hostnames. The floor has three |
| Zone items, `minDomains` unset | One zone still admits every pod of each set |

Default workers are `t3.medium` (2 vCPU, 4 GiB). Requests are API `250m` / `512Mi`, Cluster Autoscaler `100m` / `300Mi`, metrics-server `100m` / `200Mi`. The legal spread on three hostnames puts at most one of each on a node: `450m` / `1012Mi`. A drain cordons one node. Hostname `maxSkew` 1 on the two that remain allows the displaced API pod to join a node that already has one (2 and 1). The displaced Cluster Autoscaler pod and the displaced metrics-server pod join the remaining hostname that does not already hold their sibling. That can be the same node, so the busiest drain node is two API pods plus one of each system pod: `700m` / `1524Mi`. Half a `t3.medium` is `1000m` / `2048Mi`, left for the kubelet reservation and for `aws-node` and `kube-proxy` on that node. The busiest node stays under that half. The API rolling update surges one pod (`maxSurge: 1`, `maxUnavailable: 0`). On three hostnames that surge is skew 1 (2, 1, and 1) and binds on a floor node. The leader does not call `SetDesiredCapacity`. Desired stays at 3, which is under `MaxSize` 20. The `MaxLimitReached` skip runs only when desired is already `MaxSize`. That predicate is false.

Green stays at 0, so a second color is not in the floor. Postgres and Redis are not pinned to this pool. This slice does not retune their requests, the DaemonSet requests, or the instance type.

This slice does not reopen presence/CSP, Hikari/replica pool sizing, bundle zip, cosign, CDN edge, secrets rotation, VerifyFieldBounds, ClientAddress, rate-limit bucket sizes, the machine/admin HMAC, the nonce store, the download JWT `jti`, the WAF ACL, Redis AUTH, Postgres JDBC SSL, API listener TLS, the HPA metrics and replica range, the API PDB `minAvailable`, the API hostname/zone topology spread, the metrics-server zone `DoNotSchedule` item, the node-pool pin or taint, Cluster Autoscaler replica count, required hostname anti-affinity, leader election, the disruption budget, aws-node, vpc-cni, or the kube-proxy reassert hook beyond this cross-link. The [0104](0104-per-zone-node-max.md) max stays 20. The [0106](0106-api-single-zone-hostname-floor.md) floor stays 3. The [0108](0108-api-single-zone-hostname-ceiling.md) ceiling stays 3. The [0101](0101-cluster-autoscaler-leader-scale.md) flags stay `--balance-similar-node-groups=true`, `--expander=least-waste`, and `--skip-nodes-with-system-pods=false`. Do not set `minDomains`. Required hostname anti-affinity is not the follow-up. Required zone anti-affinity is not the follow-up. Catalog stays 221. No storefront. No DirectX 12 / Vulkan / Solana. No Rui sprites.

## Decision

**`max_size_per_zone` stays 20. That is the growth ceiling Cluster Autoscaler reads as the Auto Scaling group's `MaxSize`. The one-zone floor under it is 8: `maxReplicas` 3, plus Cluster Autoscaler 2, plus metrics-server 2, plus one drain node. 20 is above that floor. Twice the HPA ceiling (6), the named pods without a drain node (7), and the HPA ceiling used as a node cap (3) are refused. The live set binds on `min_size` 3, so `MaxLimitReached` at 20 is unreachable in this design. The leader cannot raise the ceiling. Kind and minikube do not apply the autoscaler file. No live AWS apply.**

1. **Ceiling.** `max_size_per_zone` stays the local `20`. The node group sets `scaling_config.max_size` to that local, not to a second literal. `zone-max-nodes=20` names it. `zone-max-floor=8` names the floor this cap must clear. `hpa-max-replicas=3` stays the pod ceiling. A value below 8, including 0, 3, 6, and 7, is refused. A value of 8 clears the floor and deletes the spare, and is refused. A value of 10 is the old starved local and is refused. A value other than 20, including 21 and 100, is refused. There is no `variable "max_size_per_zone"`.
2. **How the leader discovers it.** The two discovery tags still select the managed Auto Scaling group. `autoscaling:DescribeAutoScalingGroups` stays on the describe list. v1.36.1 `buildAsgFromAWS` copies `MaxSize` from that response. `eks:DescribeNodegroup` stays on the describe list for the pool label and the taint. It is not the max. `eks:UpdateNodegroupConfig` stays denied, with `autoscaling:UpdateAutoScalingGroup`, so the leader cannot write a higher ceiling. `SetDesiredCapacity` stays tag-scoped and stops at the group's `MaxSize`.
3. **Why the floor is 8 and why the live set never asks for it.** The floor is one node per named pod plus one drain node, for the case where those pods refuse to share. The live packing does share. `min_size` 3 is at least `maxReplicas`, at least the Cluster Autoscaler replica count, and at least the metrics-server replica count, so the anti-affinity and the API hostname item are already satisfied. The busiest steady node and the busiest drain node stay under half a `t3.medium` (`1000m` / `2048Mi`). Desired stays at 3. `MaxLimitReached` compares desired to `MaxSize`. Those are not equal.
4. **What stays.** `min_size_per_zone` stays 3. Create-time `desired_size` stays 3 and ignored after create. At least two zones. One group per subnet. The same `instance_types` list. The default stays `t3.medium`. The label `computerpets/node-pool=api`. The `NoSchedule` taint. HPA stays min 3 / max 3. Cluster Autoscaler stays 2. metrics-server stays 2. Green stays 0. Blue stays 2. `--max-nodes-total`, `--cores-total`, and `--memory-total` stay unset.
5. **What this slice does not change.** The number 20 does not move. A live group whose `MaxSize` is already 20 stays there. A group still at 10 is already above this floor; this slice does not apply, and it does not pretend a keeper has applied. The [0106](0106-api-single-zone-hostname-floor.md) keeper caveat is unchanged: a group whose desired size is still 2, or still 1, needs that bump before `min_size` 3 will apply. The HPA, the PDB, metrics-server, and the autoscaler file stay out of the kustomization. No live AWS apply.
6. **Kind and minikube.** The autoscaler file and metrics-server stay out of the kustomization. `enable_node_pool=false` does not plan the groups or the role. Kind and minikube do not apply this cap. Do not add the files to make a laptop scale. Do not set minDomains. Do not taint a kind or minikube node.
7. **Verify without a cluster.** `check-cluster-autoscaler-zone-max-floor.sh` fails when `max_size_per_zone` is not 20, when that local is below the computed floor (including 3, 6, and 7), when the local is the floor of 8 with no spare, when the local is the old 10, when the local is above 20, when the computed floor is not 8, when a replica change pushes the floor above 20, when the busiest drain node no longer fits under half a `t3.medium`, when `min_size` drops below the one-zone hostname count, when `DescribeAutoScalingGroups` drops off the describe list, when `UpdateNodegroupConfig` is no longer denied, when a root or module variable can override the local, when `minDomains` is set, or when `kustomization.yaml` lists the autoscaler file or metrics-server. `check-cluster-autoscaler-zone-max-floor.test.sh` proves those regressions. No `kubectl apply` and no `terraform apply`.

## Consequences

- The billable floor stays six on-demand workers (default `t3.medium`), three per zone. This slice does not add nodes and does not remove the cap. Peak replica count stays 3. Desired stays at the floor unless some other pod is Pending.
- On one Ready zone the live color, both Cluster Autoscaler pods, and both metrics-server pods bind on the three floor hostnames. A drain of one of those hostnames still fits on the other two. The leader does not grow the group for this set, so the group does not reach `MaxSize` 20, and `MaxLimitReached` does not fire.
- A max below 8 starves that set in the one-pod-per-node model. Twice the new HPA ceiling is that starve. The check refuses it.
- The twelve slots between 8 and 20 are unused by this design. They are not a target. Dropping them to sit on the floor is refused, because the next Pending pod after the named set would then be `MaxLimitReached`.
- `DescribeAutoScalingGroups` is the read. Changing the Terraform local does nothing to a live group until a keeper applies it. This slice does not change the local and does not apply.
- Kind and minikube do not apply the autoscaler file. One hostname still schedules both local blue replicas. Do not set `minDomains`.
- Setting the local to 3, 6, 7, 8, 10, or above 20, or growing the pinned replica counts until the floor exceeds 20, or raising a request until the busiest drain node no longer fits under half a `t3.medium`, fails `check-cluster-autoscaler-zone-max-floor.sh`.
- Catalog stays 221. No Rui sprites. `_*.py` stay untracked.
- **Next gap:** the Pending standby still does not hold the lease. A Cluster Autoscaler pod that is Pending cannot take `leases/cluster-autoscaler`, so nothing raises desired capacity for the group that would fit it. This cap is not why that pod is Pending: the floor of 3 already has the second hostname, and this slice does not apply a group whose desired size is still 1 or 2. Do not set `minDomains`. Required hostname anti-affinity is not the follow-up. Required zone anti-affinity is not the follow-up. One labeled zone still schedules both Cluster Autoscaler pods when two hostnames exist. The kube-proxy managed addon schema still rejects `tolerations`, so coverage between applies depends on the [0097](0097-kube-proxy-toleration-hook.md) hook and on the flag being true. One labeled zone still schedules both metrics-server pods when two hostnames exist. One hostname still schedules every API pod of the live color. A serving certificate that does not chain to `caBundle` (and is not a system root), or whose SAN is not `metrics-server.kube-system.svc`, still leaves `kubectl top` empty. A kubelet certificate that does not chain to `metrics-server-kubelet-ca` still leaves `kubectl top` empty.
